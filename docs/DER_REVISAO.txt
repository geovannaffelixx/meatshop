# Revisão do DER — MeatShop 3.2.0

Conferência das entidades, migrations, persistência utilizada pelos clientes e schema PostgreSQL local atualizado em 18/10/2026. O banco possui 55 tabelas de aplicação; o desenho enviado declara 30 delas. Faltam 25 entidades. A tabela técnica migrations foi excluída do DER de negócio.

## Como aplicar

Opção recomendada: substituir o conteúdo do diagrama pelo arquivo DER_ATUALIZADO.mmd. Ele contém todas as entidades e todas as FKs atuais.

Para editar o original: (1) inserir as entidades novas abaixo antes da primeira relação User||--o{UserUnit; (2) substituir integralmente cada entidade existente listada na seção seguinte; (3) substituir todas as relações antigas pelas relações finais deste documento. Não acrescentar as relações finais mantendo as antigas, pois há cardinalidades divergentes.

## Relações: substituir todo o trecho final

O lado o| admite ausência do pai porque a FK aceita NULL. O lado o{ admite zero ou vários filhos. Um filho único é representado por o| quando a FK é também PK ou possui unicidade individual. A existência de um pai não obriga que já exista um filho.

```mermaid
    User ||--o{ Address : "user_id"
    User ||--o{ AiConversation : "user_id"
    AiConversation ||--o{ AiMessage : "conversation_id"
    User ||--o| AiRateLimit : "user_id"
    Unit o|--o{ AuditLog : "unit_id"
    User o|--o{ AuditLog : "user_id"
    Unit ||--o{ BusinessHours : "unit_id"
    User ||--o| Cart : "user_id"
    Cart ||--o{ CartItem : "cart_id"
    Product ||--o{ CartItem : "product_id"
    Unit ||--o{ Category : "unit_id"
    Order ||--o{ Chat : "order_id"
    User ||--o{ Chat : "receiver_id"
    User ||--o{ Chat : "sender_id"
    Coupon ||--o{ CouponRedemption : "coupon_id"
    Order ||--o| CouponRedemption : "order_id"
    Unit ||--o{ CouponRedemption : "unit_id"
    User ||--o{ CouponRedemption : "user_id"
    Coupon ||--o{ CouponUnit : "coupon_id"
```

## Correções e limites importantes

- Renomear eliveryTracking para DeliveryTracking: o original define uma entidade com erro de digitação e utiliza outro nome nas relações.
- Remover a relação active_vehicle. Não existe active_vehicle_id em DeliveryPerson. A escolha é feita por vehicles.is_active, com índice único parcial por entregador.
- Stock.quantity, CartItem.quantity e OrderItem.quantity são decimais; Vehicle.year é inteiro; Chat.id e Notification.id são inteiros.
- UserUnit.local_role: OWNER, MANAGER, OPERATOR e DELIVERY.
- Coupon não tem discount_percentage nem discount_value. O modelo usa discount_type e discount_amount, limites, abrangência, vínculos e resgates.
- Product/Stock, Order/Payment e User/Cart possuem relação com zero ou um filho, não com vários ou obrigatoriamente um.
- Sale representa a divulgação de ofertas/banners da vitrine no módulo finance. A tabela sales não possui FK para Order, User ou Unit. Não inventar esses vínculos.
- SavedPaymentMethod permanece no banco por compatibilidade. Cadastro e escolha de cartão padrão têm endpoints descontinuados (HTTP 410); a existência da tabela não significa que esses fluxos estejam ativos.
- O diagrama completo registra FKs reais. orders.tracking_consent_user_id, delivery_tracking.delivery_person_id, payments.received_by, payment_refunds.requested_by, payments.transaction_id e payment_refunds.payment_id são referências utilizadas pela aplicação sem FK correspondente. Não foram marcadas FK.
- payment_transactions.reference é uma referência textual que pode apontar para pedido ou checkout. checkout_id e tracking_session_id são identificadores de agrupamento/sessão, não tabelas adicionais.
- Preferências, rascunhos e sessão locais do mobile, Firebase Auth e arquivos em storage não são tabelas deste PostgreSQL. Os identificadores e URLs persistidos estão representados nas entidades correspondentes.
- Os arquivos descrevem a estrutura; não contêm valores de usuários, credenciais ou tokens.

## Unicidades compostas e parciais

PK,FK nos atributos de CouponUnit indica que ambos compõem a chave primária, não que cada coluna seja única isoladamente. Restrições compostas/parciais não podem ser expressas integralmente pela cardinalidade simples do Mermaid. Abaixo estão os índices e constraints de unicidade para conferir essas regras.

- `users`: `UNIQUE (email)`.
- `users`: `UNIQUE (cpf)`.
- `units`: `UNIQUE (cnpj)`.
- `stock`: `UNIQUE (product_id)`.
- `cart`: `UNIQUE (user_id)`.
- `coupons`: `UNIQUE (code)`.
- `delivery_persons`: `UNIQUE (user_id)`.
- `payments`: `UNIQUE (order_id)`.

- `coupon_redemptions`: `UNIQUE (order_id)`.

## Referências lógicas opcionais

Inserir este bloco somente se a documentação também representar referências de aplicação. Elas não são FKs do PostgreSQL. O traço pontilhado é uma convenção deste documento para indicar essa distinção; o Mermaid não valida integridade referencial e o traço pontilhado, isoladamente, não prova ausência de FK.

```mermaid
    User o|..o{ Order : "logica: tracking_consent_user_id"
    DeliveryPerson o|..o{ DeliveryTracking : "logica: delivery_person_id"
    User o|..o{ Payment : "logica: received_by"
    User o|..o{ PaymentRefund : "logica: requested_by"
    PaymentTransaction o|..o| Payment : "logica: transaction_id"
    PaymentTransaction o|..o{ PaymentRefund : "logica: payment_id"
```

A cardinalidade opcional no lado do registro referenciado indica que a presença desse registro não é garantida por FK. Não criar uma relação fixa para payment_transactions.reference, pois sua interpretação depende do tipo de referência.
